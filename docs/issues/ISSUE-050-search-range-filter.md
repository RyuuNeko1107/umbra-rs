# ISSUE-050: `search` が要求範囲外の日食を返す（候補窓が範囲で再フィルタされない）

## 背景（実測された欠陥）

ISSUE-048 の mutation（`date.jd2().jd() + 1.0` → `* 1.0` が撃てない）を追って発見した。

`new_moon_candidates` は平均朔の探索窓（`WINDOW_HALF_WIDTH_DAYS = 1` 日）のぶん**要求範囲を両側に広げて**
候補 k を採る（偽陰性ゼロにするための意図的な広げ方で、ここ自体は正しい）。しかし
**`EclipseEngine::search` はその候補から得た日食を、最後に要求範囲で絞り込んでいない**。
結果として、**範囲外の日食が返る**。

実測（`standard_engine(bundled_time_data())`・2024-04-08 の皆既）:

| 要求範囲 | 返った件数 | event_key |
|---|---|---|
| `[2024-04-06, 04-07)` | 0 | — |
| `[2024-04-07, 04-08)` | **1** | `2024-04-08#300` |
| `[2024-04-08, 04-09)` | 1 | `2024-04-08#300` |
| `[2024-04-09, 04-10)` | **1** | `2024-04-08#300` |

## 影響

- `umbra search --from A --to B` が **[A,B] 外の日食**を列挙する。
- `umbra local --date D`（ISSUE-032）と `umbra path --date D`（ISSUE-048）はどちらも
  `[D, D+1)` を `search` して**先頭を「その日の日食」として扱う**ため、
  **`--date 2024-04-07` や `--date 2024-04-09` が 4/8 の日食を返す**。
  CLI のヘルプ・doc が謳う「指定日に起こる日食」という契約と食い違う。
- 誤差ではなく**範囲指定の意味の不一致**なので、利用者が気づきにくい（もっともらしい結果が返る）。

## 目的

`search(range)` が返す日食を、**範囲に入るものだけ**にする。

## 確定すべき仕様（要判断）

1. **どの時刻で範囲内を判定するか**: 最大食時刻（`greatest.time_utc`）が最有力。
   P1〜P4 が範囲と重なるか（区間の交差）という定義もありうる。**日食は数時間続くので、
   「範囲の端に半分だけ掛かる日食」の扱いが変わる**。CLI の「その日の日食」は最大食基準が自然。
2. **境界の開閉**: `[start, end)` か `[start, end]` か。`UtcRange` の既存規約に合わせる
   （`umbra search` のヘルプは「境界含む」と書いている＝要確認）。
3. **回帰の確認**: 既存テストには**広い範囲で件数を数えるもの**があるため、絞り込みで件数が変わる
   可能性がある。件数が変わるテストは「仕様が正された」のか「テストが範囲外を期待していた」のかを
   1 件ずつ判定する（黙って期待値を書き換えない）。

## 非目的

- `new_moon_candidates` の窓幅の変更（偽陰性ゼロの担保なので**触らない**）。
- CLI 側の日付解決の作り替え（エンジンが正しく絞れば CLI はそのままで正しくなる）。

## 受け入れテスト戦略

- 実 2024-04-08 に対し、`[04-07, 04-08)` と `[04-09, 04-10)` が **0 件**、`[04-08, 04-09)` が 1 件。
- 範囲の端に掛かる日食（最大食が範囲外だが P1〜P4 が範囲に重なる）の扱いを、確定した仕様どおりに固定。
- 既存の広範囲スイープ（件数を数えるテスト）の回帰。

## 依存

ISSUE-016/017/018（候補生成）、ISSUE-043（Engine 結線）。CLI は ISSUE-031/032/048。
