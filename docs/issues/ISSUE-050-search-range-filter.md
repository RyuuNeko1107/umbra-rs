# ISSUE-050: `search` が要求範囲外の日食を返す（候補窓が範囲で再フィルタされない）

## 背景（実測された欠陥）

ISSUE-048 の mutation（`date.jd2().jd() + 1.0` → `* 1.0` が撃てない）を追って発見した。

`new_moon_candidates` は平均朔の探索窓（`WINDOW_HALF_WIDTH_DAYS = 1` 日）のぶん**要求範囲を両側に広げて**
候補 k を採る（偽陰性ゼロにするための意図的な広げ方で、ここ自体は正しい）。しかし
**`EclipseEngine::search` はその候補から得た日食を、最後に要求範囲で絞り込んでいない**。
結果として、**範囲外の日食が返る**。

実測（`standard_engine(bundled_time_data())`・2024-04-08 の皆既）:

| 要求範囲 | 返った件数 | event_key |
|---|---|---|
| `[2024-04-06, 04-07)` | 0 | — |
| `[2024-04-07, 04-08)` | **1** | `2024-04-08#300` |
| `[2024-04-08, 04-09)` | 1 | `2024-04-08#300` |
| `[2024-04-09, 04-10)` | **1** | `2024-04-08#300` |

## 影響

- `umbra search --from A --to B` が **[A,B] 外の日食**を列挙する。
- `umbra local --date D`（ISSUE-032）と `umbra path --date D`（ISSUE-048）はどちらも
  `[D, D+1)` を `search` して**先頭を「その日の日食」として扱う**ため、
  **`--date 2024-04-07` や `--date 2024-04-09` が 4/8 の日食を返す**。
  CLI のヘルプ・doc が謳う「指定日に起こる日食」という契約と食い違う。
- 誤差ではなく**範囲指定の意味の不一致**なので、利用者が気づきにくい（もっともらしい結果が返る）。

## 目的

`search(range)` が返す日食を、**範囲に入るものだけ**にする。

## 確定仕様（2026-09-14）

1. **判定に使う時刻＝最大食（`greatest.time_utc`）**。理由:
   - 日食の**同一性**は最大食の瞬間で与えられている（`event_key` が最大食 UTC 日付 + lunation）。
   - P1〜P4 の**区間交差**で判定すると、日食は数時間続くので**隣接する 2 日が同じ日食を主張しうる**。
     `umbra local/path --date D` の「その日の日食」が一意に定まらず、本 issue が直そうとしている
     混乱がそのまま残る。
   - 「範囲の端に部分食だけ掛かる日食」は範囲外になるが、これは**範囲の意味が明確**であることと
     引き換えの、説明できる挙動である（`search` の doc に明記する）。
2. **境界は閉区間 `[start, end]`**。`umbra_core::TimeRange` の doc が「時刻範囲 `[start, end]`」と
   閉区間で定義しており、`umbra search --from/--to` のヘルプも「境界含む」と書いている。既存規約に従う。
   - 帰結（明記）: CLI の日付解決は `[D, D+1]` になるので、**最大食がちょうど D+1 の 0:00:00**
     である日食は D と D+1 の両方で返る。測度ゼロの境界であり、他の測度ゼロ境界
     （conventions の `|Δlon|=180` 等）と同じ扱いとする。
3. **候補生成は変更しない**（`WINDOW_HALF_WIDTH_DAYS` は偽陰性ゼロの担保）。絞り込みは
   `search` が**組み立て後に**行う＝候補窓は広いまま、返す集合だけを範囲に合わせる。
4. **回帰の扱い**: 絞り込みで件数が変わる既存テストは、「仕様が正された」のか
   「テストが範囲外を期待していた」のかを 1 件ずつ判定する（**黙って期待値を書き換えない**）。

## 非目的

- `new_moon_candidates` の窓幅の変更（偽陰性ゼロの担保なので**触らない**）。
- CLI 側の日付解決の作り替え（エンジンが正しく絞れば CLI はそのままで正しくなる）。

## 受け入れテスト戦略

- 実 2024-04-08（最大食 18:17 UTC）に対し、日単位の要求で **4/7 と 4/9 は 0 件・4/8 は 1 件**
  （現状は 4/7・4/9 でも 1 件返る＝本 issue の再現）。
- 最大食が範囲外だが P1〜P4 が範囲に重なる日食は**返らない**（確定仕様 1 の帰結を固定）。
- 閉区間であること: 最大食時刻ちょうどを `start` に、また `end` に置いた範囲で**返る**。
- 候補窓は変えない: 範囲の外側 ±1 日に最大食がある日食が**返らない**ことを直接固定。
- 既存の広範囲スイープ（件数を数えるテスト）の回帰。

## 依存

ISSUE-016/017/018（候補生成）、ISSUE-043（Engine 結線）。CLI は ISSUE-031/032/048。

## 完了状況（2026-09-15・strict）

**完了**。`search` は**最大食時刻が要求範囲（閉区間）に入る日食だけ**を返すようになった。

### 実装

`EclipseEngine::search` の組み立て後に `retain` で絞り込む（候補生成は無変更＝偽陰性ゼロの担保を維持）。
比較は **2 要素表現のまま `JulianDate2::days_since`** で行う。実装レビューの指摘により、当初の
`jd()`（合算 f64）から変更した: `julian.rs` が `jd()` を「表示・粗い比較用。精度クリティカルな差分には
使わない」と定めており、合算は ~4.6e-5 s を失って ±1 s 目標を削る（conventions §11 の禁止パターンにも該当）。

### 既存テストの回帰 1 件 — **テスト側の誤りだったと判定**

`path_center_line.rs` の `real_2017_eclipse_center_line_crosses_north_america` が赤くなった。
原因は探索窓が `[2017-08-20 12:00, 2017-08-21 12:00]` ＝ **最大食（同日 ~18:26 UTC）を含まない**こと。
**従来は `search` が候補窓（±1 日）で拾った範囲外の日食を返していたため偶然通っていた**。
窓を 2017-08-21 の暦日全体へ是正した（期待値ではなく**入力の誤り**を直した＝§確定仕様 4 の判定）。
**この 1 件以外に workspace 全体で回帰なし**。本欠陥が実際に「もっともらしい誤答」を生んでいた実例。

### 検証

`crates/umbra-eclipse/tests/search_range_filter.rs`（新規・SLOW 5 本）:
再現（4/7・4/9 が 0 件・4/8 が 1 件で event_key 一致）／閉区間の両端（最大食ちょうどを start・end に置く）／
1 秒外は 0 件／**P1〜P4 は重なるが最大食が範囲外なら返らない**（§確定仕様 1 を区間交差実装から守る）／
広範囲で複数件・昇順・全件が範囲内。オラクルは全て**エンジン自身の出力から導出**（外部数表なし）。
